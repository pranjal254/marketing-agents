Architecture Overview

Technical build specification for 5 AI agents covering the first three sub-processes of the LevelShift Content to Campaign process: Campaign Intake & Planning (Campaign Request Intake; Audience & Offer Definition; Asset Inventory & Workflow Setup), Content Production & Assembly (Content Drafting; Content Collaboration & Iteration; Campaign Asset Packaging), and Compliance Review & Approval (Review Routing; Compliance & Brand Checks; Approval Sign-off). Each agent is an independently deployable unit orchestrated by the ShiftAI Execution Studio, communicating through the inputs/outputs and connections described and sharing state via the Campaign Context Store.

Agent names follow the TO-BE agent inventory already defined in the LevelShift Marketing Process Document — the Campaign Identification agent, the Campaign-in-a-Box Orchestrator, the Content Repurposing Agent (Section 4.2 fan-out engine) and the Quality Gate agent (extended here with review routing and sign-off recording) — plus a Content Collaboration & Iteration agent for the sub-step the TO-BE table implies but does not name. Five build units cover all nine Phase 1 subprocesses with 35 of 46 step-level activities system-executed (76%); consolidation reduces build surface, not automation.

Grounding constraints (from the LevelShift Marketing Process Document): OneDrive is the content repository and campaign workspace backbone; the LLM runtime is Claude (Anthropic API), consistent with the existing campaign-master skill; Salesforce and Pardot are explicitly excluded from Phase 1 — CRM/marketing-automation integration begins at sub-process 4 (Campaign Launch & Publishing), out of scope. All Section 5 governance guardrails apply to every agent: BC/F&O independence, Copilot = D365-cloud-only, "ShiftAI" as one word, banned-terms filtering, no unsourced competitor/ROI claims, positive non-urgency tone, and no external publish/send without the existing human approval gates.

V2 Cross-Agent Standards (apply to all 5 agents)

A — Cost model & optimization. Model selection is confirmed against the current Anthropic lineup: claude-opus-5 where judgment and writing quality pay (Agents 2 planning, 3), claude-sonnet-5 everywhere else, deterministic modules (packaging, rules pass, routing) run with no LLM. Mandatory optimizations: prompt caching on the versioned rules pack, brand guidelines and system prompts (~90% off cached input reads); Batch API for the Agent 3 derivative fan-out (50% off; fits the 20-min fan-out SLA); Haiku 4.5 ($1/$5) is the approved downgrade path for Agent 4 feedback normalization if volumes grow. Token usage and cost per run are first-class telemetry on every agent (see B), not only Agent 3.

StandardRequirement
B — Telemetry envelopeEvery agent emits telemetry conforming to the ShiftAI Telemetry Standard (STS) v1.1, read natively by Execution Studio. Every event carries: shiftai.timestamp, shiftai.event.type, trace / run / span / parent-span IDs, process → subprocess → activity context (as OTel resource attributes), a generalized business_object (type + ID + transaction ID), gen_ai.* model and token usage, shiftai.cost.* with mandatory cost.scope (run_total vs span_incremental — prevents double-counted rollups), latency breakdown (llm / api / queue / total), state.previous / state.current / state.reason for journey reconstruction, sla.status / due_at, business_outcome, and prompt-template + config versions. Execution Studio renders the full campaign journey from trace_id alone; a version-drift dashboard surfaces any run where model / prompt / rules-pack versions diverge from the fleet baseline. Existing business metrics per agent remain unchanged.
C — Human handoff & error taxonomyEvery escalation, gap request, conflict surface, override and fallback is recorded as an STS human_gate event using the shiftai.learn.* namespace: reason_code (versioned taxonomy), agent_recommendation vs human_action (the delta is the training signal), label (false_positive / false_negative / correct), calibration_id, scenario_hash and occurrence_count_90d, plus hitl.decision / actor.role and decision_latency_ms. Reason codes come from a versioned taxonomy (e.g. unclassifiable_bu, duplicate_disputed, thin_intel, unsourced_claim, feedback_conflict, infeasible_timeline, sla_breach, tool_failure). The Agent 5 calibration-log pattern (false-positive / false-negative labeled examples) is extended to all agents: any human override of an agent output is captured as a labeled example. This event stream is the training corpus for the sub-process 5 learning module.
D — Autonomy ScoreEach agent's qualitative autonomy statement is supplemented with a quantitative Autonomy Score, computed per agent per week from the B/C event streams: autonomy_rate = steps completed without human touch ÷ total steps; escalation_rate; override_rate = human reversals of agent decisions ÷ agent decisions; handoff_latency_p95. Composite score and weighting to follow Manoj's autonomy measurement logic — formula to be mapped field-by-field onto this schema on receipt (owner: AiCoE; all required raw fields are already emitted by B and C, so the formula is a dashboard change, not an agent change). Target trajectory: autonomy_rate rising wave-over-wave with override_rate flat or falling — the GTM proof line. Self-improvement loop (V2.1): when one scenario_hash accumulates N consistent human decisions (default N=5 in 90 days), the system emits an STS autonomy_promotion event proposing a rules-pack update or scenario-scoped autonomy upgrade; the promotion itself is a human-approved change, gated by saams.evidence_grade, and every promotion/demotion is a first-class audited event — autonomy is earned per scenario, never assumed globally.
Sections B–D are additive: no existing guardrail, human gate or approval authority changes. Human checkpoints remain structurally enforced; these standards make them measurable.

Campaign Identification Agent

AI Agent

The TO-BE design's Campaign Identification agent ("proposes opportunities from the BU plan and event calendar"), built out into the single front door for campaign demand. It captures campaign requests from the quarterly marketing plan, BU plans, vertical priorities (Financial Services, Manufacturing, Technology) and the event calendar — plus ad-hoc requests — and normalizes each into a complete, structured campaign brief. It validates completeness, detects duplicates and calendar conflicts against in-flight campaigns, classifies the request (BU, vertical, Type 3/4 segment relevance, channel mix), and routes the brief to the BU Campaign Lead for approval, upgrading the manual identification step (AS-IS 3.1 step 1; 3.2 step 1) so downstream planning always starts from a validated brief rather than a loose topic.

Max Tokens8,000 (structured brief output)InvocationEvent-driven: new row/file in the intake form or watched OneDrive folder; also callable on demand from Execution Studio

Implementation Tasks

StepTask
1Ingest campaign requests from three entry points: the standard intake form (Microsoft Forms/Excel), new items detected in the quarterly marketing plan sheet, and event-calendar entries flagged for campaign support; normalize all three into a common request record.
2Validate the request against the brief template schema: objective, business unit, vertical, target segment (Type 3 / Type 4 / standard), offer or topic, intended channels, timeline, owner, and budget flag; enumerate every missing or ambiguous field.
3Query the campaign calendar and Campaign Context Store for open campaigns with overlapping BU + vertical + topic; flag duplicates and timing conflicts (e.g. two Technology BU email campaigns targeting the same audience window).
4Enforce the BC/F&O independence rule at intake: a request that mixes Business Central and F&O in one campaign concept is split or flagged, never silently merged.
5Classify the request: campaign type (demand gen, offering launch support, event follow-up), priority derived from vertical priority and BU plan linkage, and channel mix — noting events as the standout channel for Type 3/4 segments per the AS-IS channel notes.
6Where fields are missing, draft a targeted gap request back to the requester (specific questions, not a generic bounce) and hold the brief in awaiting_input rather than passing an incomplete brief downstream.
7Assemble the structured campaign brief document in the campaign workspace (Word) using the standard template, with all classification fields, provenance of the request source, and links to the originating plan rows or calendar entries.
8Route the completed brief to the BU Campaign Lead for approval and record the routing event; the brief cannot advance until an explicit human approval is captured.
9Persist a compact intake summary (request source, classification, conflicts found, validation results, approval status) to the Campaign Context Store for reuse by the Campaign-in-a-Box Orchestrator.
10Emit structured telemetry per request — completeness score at first submission, gap-request count, duplicate flags raised — so the intake funnel itself can be measured and improved.

Campaign-in-a-Box Orchestrator

AI Agent+ Deterministic packaging module

The TO-BE design's Campaign-in-a-Box Orchestrator: "assembles the full package (intel, calendar, outlines, touchpoints) in one pass." From an approved brief it produces the complete campaign foundation — sourced competitive/market intel (SemRush plus the OneDrive intel library, with the accuracy rule enforced: no unsourced competitor claims), the audience & offer pack (vertical, Type 3/4 segments, personas, offer framing with per-claim provenance), the reuse-scanned asset checklist with reuse/adapt/create decisions, content outlines, the back-planned calendar and workflow plan, and the standardized campaign workspace. At the end of production its deterministic packaging module assembles the literal Campaign-in-a-Box: completeness verification against its own checklist, naming/metadata enforcement, hashed final-version snapshots, and the machine-readable package manifest handed to the Quality Gate. One agent owns the campaign's plan and its package, so the checklist that plans the work is the same record that verifies it.

Model / RuntimeClaude Opus 5 (claude-opus-5) via Anthropic API — adaptive thinking, effort high, streaming. Packaging module: Execution Studio workflow engine (no LLM)SLA TargetPlanning pass p95 < 15 min from approved brief; packaging run < 60 seconds
Max Tokens16,000 (planning outputs)InvocationPlanning: triggered on brief approval. Packaging: triggered when all checklist assets reach content-confirmed; re-runs on rework re-entry

Implementation Tasks

StepTask
1Load the approved campaign_brief and intake context; reject briefs not in approved state with a structured error.

3Define the target audience — vertical (FinServ / Manufacturing / Technology), Type 3 / Type 4 segment applicability with rationale, buyer personas with role-level pains, exclusions — and weigh channel emphasis using documented AS-IS performance (events dominate Type 3/4 opportunity creation; email/SEO carry standard BU volume).
4Frame the offer: value proposition, differentiators (including ShiftAI structural independence where relevant), proof points each mapped to a source, CTA per funnel stage; draft persona-level messaging angles in LevelShift tone, applying the LevelShift Brand Guidelines (positive, no urgency/fear framing, banned terms filtered, BC/F&O independence, Copilot D365-cloud-only).
5Search the OneDrive content repository by BU/vertical/topic/asset type and score candidates for reuse fitness; produce the asset checklist from the standard Campaign-in-a-Box composition with an explicit reuse / adapt / create decision and rationale per required asset — never marking an asset create without a repository search.
6Draft content outlines for every create/adapt asset, seeded from the confirmed messaging angles, so the Content Repurposing Agent starts from an approved skeleton.
7Back-plan the content calendar and workflow plan from the campaign window — honoring the 2-researched-blogs/month capacity rule and every review gate — create the campaign workspace from the versioned folder/naming template, initialize the status tracker, and register every planned asset in the Context Store.
8Route the audience & offer pack and the workflow plan to the Marketing Lead / BU Campaign Lead for confirmation; apply changes as deltas; escalate infeasible timelines with explicit trade-offs instead of silently compressing review gates.
9[Packaging module] On all-assets-confirmed: compute the completeness diff against the asset checklist (missing / extra / version-mismatch); block packaging with an actionable report if the diff is non-empty; verify every asset carries a human confirmation record.
10[Packaging module] Validate naming convention and required metadata per asset (auto-correct only unambiguous cases); snapshot final versions into the final-assets folder as copies; compute a content hash per packaged asset so post-packaging edits are detectable.
11[Packaging module] Assemble the Campaign-in-a-Box manifest — asset inventory with file IDs/versions/hashes, calendar reference, touchpoint copy set, sales collateral, call scripts, claim-lineage index, checklist mapping — register it as packaged_pending_compliance and hand it to the Quality Gate & Approval Agent. 12[Packaging module] On gate or approval returns: re-open only affected assets, track re-packaging deltas, re-hash on re-entry; emit the packaging summary to the status tracker.

Content Repurposing Agent

AI Agent

The TO-BE design's Content Repurposing Agent (Section 4.2, Content Distribution & Repurposing Engine) — the production engine of Phase 1 and its highest-value build.
